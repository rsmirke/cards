# 29. Tags

- Status: Accepted
- Date: 2026-10-17
- Amends: SPEC §3 (`tags` is unique by a name key, not by its exact name)
- Amended: 2026-10-17, an imported tag with the name of an existing tag is mapped onto it, not a conflict

## Context

SPEC §3 plans flat tags on cards (`tags`, `card_tags`), and §4.4 and §4.6 will use them: a tags field in the editor, a tag filter, "add tag" on several cards. The tags slice also has to put them in the export (format version 2). Three questions needed an answer: when two names are the same tag, what a tag name may hold, and whether a tag is ever deleted.

## Decision

**Unique by name key, like decks.** `tags(id, name, name_key UNIQUE)` (migration 0008). The key is `name_key`, the same function as decks' key (ADR 0010; `deck_name_key` is now a thin alias): trimmed, NFC, lower-cased. So "Maths", "maths" and "MATHS" are one tag. Adding a tag by a name that already has a tag reuses that tag with its own spelling. `card_tags(card_id, tag_id)` has a composite primary key and no other columns.

**Names.** Trimmed, not empty, at most 256 bytes, no NUL (GTK, as for decks and cards), and **no comma**: the editor's field will be a comma-separated list (SPEC §4.4), and a comma inside a name could not be typed back.

**Never deleted.** `remove_tag` removes the link only, and a tag that no card uses stays. If unused tags were deleted, removing "maths" from every card and adding it again would give it a new id, and every export made before would need the import's name mapping to find it. Keeping the tag means a name keeps one id for good, so this database's own exports always match it by id. A "delete tag" later would need a soft delete, as decks have.

**Tags do not change the card.** Adding or removing a tag leaves `cards.updated_at` alone, so the import's comparison of card content (ADR 0017) does not see tag changes as edits. Deleted cards keep their tags, and a deleted card cannot be tagged.

**Store API.** `tags()` (all, by key), `card_tags(card)`, `add_tag(card, name)`, `remove_tag(card, tag)`. The UI comes later.

## Consequences

- Two machines that each create "maths" get two ids. *Amended 2026-10-17:* merging their exports is **not** a conflict. A tag is only its name, so the file's tag is mapped onto the database's tag with the same name key, and the file's cards get the database's tag (ADR 0017's merge rules). The database keeps its id and its spelling. Decks still conflict on a name, because a deck has content (its cards) that a mapping would merge silently. Since the mapping is decided by name on every plan, re-importing stays a no-op. The mapped tag's id is not stored, so an export of the merged database has one "maths" tag, the database's own.
- Removing a tag from a card does not travel through an import: importing an older file that still has the link adds it back, as an import adds every row it does not find (it never deletes).
- Tags are listed by key, which is byte order of the lower-cased name ("maths" before "économie"). Showing them sorted for a language is the UI's job.
